# BI Module — Implementation Plan

> **Estado:** ✅ TODAS LAS FASES IMPLEMENTADAS (1, 1.5, 2, 3, 4) en v2.0.0.
>
> Documento histórico — describe el plan ejecutado.
>
> Para el diseño completo: `docs/superpowers/specs/2026-05-10-bi-module-design.md`.

**Goal original:** Entregar BI Esencial MVP — un cliente activa el addon `bi` desde su panel y abre `/dashboard/bi/` con dashboards de monitoreo prediseñados, exportes y alertas por umbral.

**Estado final:** El módulo se entregó completo en 7 commits:
- `feat(bi)` Fase 1 — catálogo + DSL + dashboard Resumen
- `feat(bi)` admin toggles + sidebar + cron refresh + dashboards Ventas/Productos/Clientes
- `feat(bi)` exportes Excel + PDF
- `feat(bi)` alertas por umbral (CRUD + cron evaluador)
- `feat(bi)` Fase 1.5 — Inventario y Créditos (+2 vistas materializadas)
- `feat(bi)` Fase 2 (Pro) — dashboards custom + builder de vistas
- `feat(bi)` Fase 3 (Pro) — forecast + segmentos + campañas
- `feat(bi)` Fase 4 (Pro Avanzado) — anomalías + cohortes + canasta + Q&A AI

**Architecture:** Vistas materializadas en Postgres (refrescadas por cron) → DSL de query (`POST /api/bi/query`) → feature module `features/bi/` → páginas en `/dashboard/bi/*`.

**Tech Stack:** Next.js App Router · Prisma · PostgreSQL (Neon) · Recharts · ExcelJS · @react-pdf/renderer · Upstash Redis (cache de queries) · NextAuth.

**Spec:** `docs/superpowers/specs/2026-05-10-bi-module-design.md`

- [ ] **Step 2.1: Catálogo de measures (single source of truth)**
  - `MEASURES`: `sales_total`, `invoice_count`, `ticket_avg`, `units_sold`, `unique_customers`, `gross_sales`, `discounts`.
  - Cada measure tiene: `id`, `label`, `unit` (currency/count/percentage), `aggregator` (sum/count/avg), `source` (vista materializada).

- [ ] **Step 2.2: Catálogo de dimensions**
  - `DIMENSIONS`: `day`, `week`, `month`, `product`, `customer`, `sucursal` (cuando aplique).
  - Cada una con: `id`, `label`, `field` (columna en la vista), `type` (date/string/number).

- [ ] **Step 2.3: Tipos del DSL**
  - `BIQuery = { measures: MeasureId[], dimensions: DimensionId[], filters?: BIFilter[], dateRange?: {from, to}, sortBy?: ..., limit?: number }`.
  - `BIQueryResult = { rows: Record<string, unknown>[], meta: { totalRows, executedAt, source } }`.

- [ ] **Step 2.4: `QueryService.run(query, ctx)`**
  - Valida query (Zod) → resuelve la vista materializada que cubre esa combinación de measures/dimensions → genera SQL parametrizado con `$queryRawUnsafe` (whitelist de columnas, NUNCA interpolación de input) → ejecuta con `clientId` forzado.
  - Cache key: `bi:query:<clientId>:<hash(query)>`. TTL 60s.

## Riesgos durante la implementación

1. **`PosSale` no existe como modelo separado.** Las ventas POS viven en `Invoice` con `paymentMethod`/`status`. Las vistas materializadas filtran `status IN ('EMITTED', 'INTERNAL', 'CERTIFIED')` para incluir tanto facturas certificadas como ventas internas POS.
2. **Multi-tenant scale.** Las vistas materializadas son globales (no por client) pero indexan `(client_id, ...)`. Si un Enterprise satura, particionar por `client_id` con `pg_partman` o mover a vistas separadas por client.
3. **Refresh concurrente.** `REFRESH MATERIALIZED VIEW CONCURRENTLY` requiere índice único en cada vista. Cada vista debe declarar uno (ej. `(client_id, day)` o `(client_id, product_id)`).
4. **Cache invalidation.** TTL de 60s es conservador; al emitir/anular factura podemos invalidar `bi:query:<clientId>:*` desde el servicio de invoice. Fase 1.3.
